## 1. Migration runner

`scripts/migrate-postgres.js` is unchanged in mechanism: a versioned, ordered, idempotent list of
migrations applied inside a transaction per migration, recorded in `schema_migrations(version, name,
checksum, applied_at)`, run with `npm run db:migrate`. Two migrations were added to the end of the
list; **existing entries were not edited** (editing an applied migration would change its checksum).

The runner reported `schemaVersion: 7` against a freshly migrated PostgreSQL.

### Migration 6 — `card_destination_provenance`

```sql
ALTER TABLE cards ADD COLUMN IF NOT EXISTS place_id VARCHAR(255);
ALTER TABLE cards ADD COLUMN IF NOT EXISTS source_url VARCHAR(2048);
ALTER TABLE cards ADD COLUMN IF NOT EXISTS resolution_status VARCHAR(16);
ALTER TABLE cards ADD COLUMN IF NOT EXISTS resolution_method VARCHAR(32);
ALTER TABLE cards ADD COLUMN IF NOT EXISTS resolved_at TIMESTAMP;
ALTER TABLE cards ADD COLUMN IF NOT EXISTS resolved_business_name VARCHAR(255);
ALTER TABLE cards ADD COLUMN IF NOT EXISTS resolved_business_address VARCHAR(512);
```

Every column is nullable with no default, so existing rows keep `NULL` and are untouched. No column is
dropped, renamed, narrowed or back-filled. `review_url VARCHAR(2048)`, `active`, `secret_hash`,
`code`, `demo`, `activated_at` are all left exactly as they were.

### Migration 7 — `resolution_jobs_and_audit`

```sql
CREATE TABLE IF NOT EXISTS resolution_jobs(
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  job_token VARCHAR(64) NOT NULL UNIQUE,                      -- opaque 32-byte secret (base64url)
  status VARCHAR(16) NOT NULL DEFAULT 'pending'
    CHECK(status IN ('pending','running','success','failed','expired','inconclusive')),
  input_url VARCHAR(2048) NOT NULL,                           -- original source URL
  binding_hash CHAR(64) NOT NULL,                             -- sha256(cardCode|inputUrl)
  card_code VARCHAR(32), created_by VARCHAR(80) NOT NULL DEFAULT 'public',
  place_id VARCHAR(255), review_url VARCHAR(2048),
  business_name VARCHAR(255), business_address VARCHAR(512), method VARCHAR(32),
  attempts INTEGER NOT NULL DEFAULT 0, max_attempts INTEGER NOT NULL DEFAULT 3,
  error_code VARCHAR(64), error_message VARCHAR(512),
  worker_id VARCHAR(64), locked_at TIMESTAMP, next_attempt_at TIMESTAMP,
  created_at/updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  started_at/ finished_at TIMESTAMP, expires_at TIMESTAMP NOT NULL);

CREATE INDEX idx_resolution_jobs_status  ON resolution_jobs(status,created_at);
CREATE INDEX idx_resolution_jobs_binding ON resolution_jobs(binding_hash,status);
CREATE INDEX idx_resolution_jobs_expires ON resolution_jobs(expires_at);
CREATE UNIQUE INDEX uq_resolution_jobs_active ON resolution_jobs(binding_hash)
  WHERE status IN ('pending','running');                      -- at most one in-flight job per binding

CREATE TABLE IF NOT EXISTS resolution_audit(...);              -- actor, action, card_code, old/new url,
CREATE INDEX idx_resolution_audit_card ON resolution_audit(card_code,at DESC);
```

Both migrations are `IF NOT EXISTS`-guarded and therefore idempotent and re-runnable.

## 2. Persisted provenance

| Field | Column | Written when |
|---|---|---|
| Original source URL | `cards.source_url` (and `resolution_jobs.input_url`) | activation / destination update |
| Genuine Place ID | `cards.place_id` | only from a verified resolution result |
| Verified review URL | `cards.review_url` | activation / destination update |
| Resolution status | `cards.resolution_status` (`'verified'`) | activation / destination update |
| Resolution timestamp | `cards.resolved_at` | activation / destination update |
| Verification method | `cards.resolution_method` (`manual` \| `playwright` \| `playwright+places` \| `places-api` \| `backfill`) | activation / destination update |
| Resolved business identity | `cards.resolved_business_name`, `cards.resolved_business_address` | activation / destination update |
| Job history | `resolution_jobs` row (input, candidate Place ID, review URL, method, attempts, errors, timings) | worker |
| Change history | `resolution_audit` row | destination update / backfill |

## 3. One-time activation, exactly once

`POST /api/activate` still runs a single transaction:

```
BEGIN
  SELECT id,active,secret_hash FROM cards WHERE code=? FOR UPDATE      -- row lock (unchanged)
  reject if missing / already active / wrong activation code
  [job path] SELECT id FROM resolution_jobs
             WHERE job_token=? AND card_code=? AND status='success'
               AND review_url=? AND expires_at > CURRENT_TIMESTAMP    -- re-validated inside the tx
  UPDATE cards SET active=1, review_url=?, activated_at=now(),
                   secret_hash='consumed:<sha256(code)>', activation_code_encrypted=NULL,
                   place_id=?, source_url=?, resolution_status='verified',
                   resolution_method=?, resolved_at=now(),
                   resolved_business_name=?, resolved_business_address=?
   WHERE id=? AND active=0
COMMIT
```

- The `WHERE active=0` guard plus the affected-rows check makes the one-time code single-use even
  under concurrent requests; a replay returns `409`.
- The conditional `active=0` update and the `FOR UPDATE` lock are the pre-existing protections and are
  preserved unchanged.
- **No browser automation runs inside this transaction** (or in any transaction): the job is already
  terminal by the time activation runs.

## 4. A job cannot be repurposed

`resolution_jobs` is bound to `(card_code, input_url)` through `binding_hash`, and the activation
route requires **all** of the following before writing:

| Attempt | Result |
|---|---|
| Job bound to a different card | `403` (`job.card_code !== code`) |
| Job not yet finished | `409` |
| Job carries a Maps link instead of an official review URL | `409` |
| Submitted `reviewURL` differs from the job's verified URL | `400` |
| Job expired (checked **both** before and inside the transaction) | `409` |
| Unknown/forged job token | `400` |
| No job token and a non-official URL | `400` — a raw Maps link is **never** stored as a verified destination |

Client-submitted Place IDs are not used at all: `place_id` is copied from the job row only. The
generated review URL is likewise never taken from the client when a job is used.

## 5. Legacy data compatibility

- Existing cards keep their `review_url` verbatim; the new columns stay `NULL` until a card is
  explicitly re-pointed (Phase 2E). Nothing in this phase rewrites existing rows.
- Cards activated before this feature still redirect through the untouched `/c/[code]` path.
- Cards holding Maps/short links keep working *as before* (they redirect to the Maps page) — the
  regression is fixed only when an administrator applies a verified destination.
- `activation_code_encrypted` is still nulled on activation and still populated on (re)issue, so old
  behaviour for existing codes is unchanged. The activation-code column set was not altered.
- Demo scoping (`demo` flag) is respected by both new endpoints, so demo rows are never mixed with
  production rows.

## 7. Operational notes and limitations

1. **These migrations have NOT been applied to production.** They are additive and safe to run
   (`npm run db:migrate`), but that is an explicit deployment step, deliberately not executed here.
2. `resolution_jobs` grows by one row per (card, URL) resolution request plus retry attempts; rows are
   never deleted automatically. A retention job (e.g. delete terminal jobs older than 30–90 days) is
   recommended before high-volume use — the indexes support it (`expires_at`, `status,created_at`).
3. `resolution_audit` is append-only by design (no API deletes it).
4. `review_url` remains `VARCHAR(2048)`; generated URLs are ~70 characters, so no widening is needed.
5. Historical cards are intentionally not back-filled automatically; see Phase 2E for the opt-in,
   dry-run-first backfill.
